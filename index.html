What we checked

Every rule comes from the spec's own guidance, not from opinion. Tools are discovered via document.modelContext.getTools() and called with arguments synthesised strictly from their declared inputSchema, twice, so the response can be compared against what the tool claimed.

Method, and three bugs we hit doing it

A verification tool that produces false positives is worse than none, so these are published rather than fixed quietly.

Transport success is not input acceptance.
A tool that correctly rejects a call usually returns {"isError":true} rather than throwing. Our first detector only caught exceptions and reported 67 findings that were all wrong — 68% of every tool scanned. corpuslaw.us and b2a.bluepillow.com were both verified correct by hand.
WebMCP results are multiply encoded.
executeTool() returns {content:[{text:"..."}]} where the text is itself a JSON string, so "isError":true arrives escaped and every substring check silently misses. Peeling the layers cut the count 67 → 48 → 6.
"I did not look in time" is not "there is nothing there".
Tools register after client-side JS runs. Probing too early reported three live sites as having zero tools; all three had 2–4. A zero result is now re-checked with fresh contexts before it is believed.
Not verified: three entries were unreachable from one network and may be fine elsewhere. A verification report that hides its own uncertainty is worth nothing.

What a fix looks like

  1. Land outputSchema in the spec (issue #9) and adopt it. A tool that declares its return type can be checked; one that does not cannot.
  2. Document every input field with units and format.
  3. Make schema and implementation agree where they currently disagree.
  4. Verify registry submissions automatically, so entries advertising absent tools are caught on submit.
